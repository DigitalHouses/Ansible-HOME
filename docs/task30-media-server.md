## Продолжение новой VM после Import (11.11.2026)

## Дисковые действия №30 — актуально на 11.11.2026

Выбор оператора в Semaphore **окончателен**: дополнительных согласований
или проверок старых GUID, WWN, размера, серийника, разметки,
здоровья старого пула и topology **нет**.

- **Import**: если именованный ZFS-пул ещё не импортирован, выполнить
  штатное `zpool import -f <pool>`. Никаких `wipefs`, `sgdisk`,
  `zpool destroy` или создания нового пула в ветке Import.
- **Erase**: выбрать ровно один физический SATA-диск в VM (не системный),
  остановить потребителей данных, уничтожить старый именованный пул
  при его наличии и выполнить `wipefs`, `sgdisk --zap-all`,
  `zpool create -f`. **Все данные на выбранном диске будут потеряны.**

PCI определяется автоматически из текущего PVE (см. следующий раздел).
Прежние SATA/GPU-адреса в приватном manifest игнорируются.
Никаких изменений в работающих VM или дисках при обновлении кода нет.

Сведения о более ранних preflight/GUID проверках ниже — история разработки,
не описание актуального поведения задачи №30.

## Автоматическое PCI passthrough — актуально на 11.11.2026

№30 **не читает** исторические адреса GPU и SATA из приватного
`media_vm.yml` для настройки PCI. При каждом запуске по
`lspci -Dnn` на текущем PVE выбираются первая SATA AHCI-функция
(PCI-класс `0106`) и видеоконтроллер (класс `0300/0380`).
Текущая аппаратная конфигурация PVE владельца:

- SATA: `0000:00:17.0`
- Intel UHD Graphics: `0000:00:02.0`

Выбранные адреса используются непосредственно в `qm set --hostpci`.
Устаревшие PCI в site manifest не нужно исправлять для №30.
Для **Import** после запуска VM выполняется обычный
`zpool import -f serzhan-pool`; ZFS самостоятельно обнаруживает
доступный пул по подключённым гостю дискам. Проверок диска по
GUID/WWN/серийному номеру, старому PCI, топологии или разделам **нет**.
При выборе **Erase** создаётся новый пул на SATA-диске гостя;
стирание системного диска VM по-прежнему запрещено.

## Linux root медиасервера и PBS root@pam — только №05 (10.11.2026)

**Единственный источник:** защищённое поле `Media VM Linux root / PBS root@pam — пароль (пусто = сохранить)` в задаче **№05 Credentials**, сохранённое в Semaphore Variable Group как `DH_MEDIA_ROOT_PASSWORD`. Ввод нового значения в №05 **только сохраняет** его, но не изменяет пароль текущей VM до запуска №30. Пустое поле №05 сохраняет прежний секрет без стирания. Длина нового пароля — 8–128 символов, проверяется до записи.

**№30** не содержит собственного поля пароля. Режим `apply + keep` применяет пароль из №05 к Linux `root` существующей VM, `apply + create/recreate` применяет его к новой VM. Если секрет №05 отсутствует, `keep` не меняет пароль, но `create/recreate` останавливаются **до** VM-операций (`MEDIA30_ROOT_PASSWORD_REQUIRED_IN_TASK_05`), чтобы не оставить новую VM с заблокированным root. После применения `passwd -S root` проверяется на состояние `P` (пароль задан и не заблокирован).

Linux `root` VM — это также вход PBS `root@pam`. Он **не совпадает по назначению** с root PVE (`DH_PVE_ROOT_PASSWORD`), Samba, Webmin-only администратором или отдельной учётной записью PBS `admin@pbs`. Используется нативный Ansible `user` с SHA-512 crypt hash, `no_log: true`. Значение не выводится в журналы, private site GitHub repo, ZFS credentials или портал. Ручная смена на VM будет заменена значением №05 при следующем `apply` №30.

## Lidarr и публичные русскоязычные индексеры — 11.11.2026

После первого живого запуска Lidarr (Semaphore #34) обнаружилось отличие
его `POST /api/v1/rootfolder` от Radarr/Sonarr: тело из одного
`path` возвращало HTTP 400. Исправление использует официальные
поля Lidarr `RootFolderResource`: `name`, `path`,
`defaultMetadataProfileId`, `defaultQualityProfileId`,
`defaultMonitorOption`, `defaultNewItemMonitorOption` и
`defaultTags: []`. Профили берутся из локального Lidarr API,
не захардкожены. Другие Servarr запросы не меняются. Этот код
не создаёт ZFS datasets и не затрагивает существующие медиафайлы.

Lidarr: официальный Linux x64 релиз `v3.1.6.5079`, SHA-256 из
GitHub release asset, через тот же native Servarr installer, что
Radarr/Sonarr. Сервис `lidarr.service`, LAN `:8686`,
библиотека `/<pool>/media/music`, qBittorrent категория
`lidarr` (папка `media/downloads/complete/music`), привязка
к Prowlarr и общему паролю владельца; задача №31 тоже поддерживает
смену пароля Lidarr.

Отдельно для сайта владелец может указать только
`media_vm.prowlarr_public_indexers`, содержащий идентификаторы
официальных публичных Cardigann indexer definitions. Для
`serzhan-home` выбран минимальный набор без регистрации:
`rutor`, `noname-club`, `megapeer`, `newstudio`.
RuTracker/Kinozal не включаются — необходима учётная запись.
№30 использует собственный API Prowlarr: существующие источники
сохраняет, отсутствующие добавляет только при успешном штатном
`/api/v1/indexer/test`. Недоступные в момент установки публичные
сайты пропускаются с явным статусом в логе, не создавая неработающие
источники и не прерывая весь №30. Никакие аккаунты, FlareSolverr
или отдельный Jackett не устанавливаются.

Для других сайтов Lidarr включается только при
`applications.lidarr: true`, а индексеры — только при
присутствии `prowlarr_public_indexers` в site manifest.
Для уже существующей VM применять только `Apply + Keep + Import`;
данные на диске не изменяются.

## rclone v1.76.0 + официальный Web GUI (08.11.2026)

№30 устанавливает **официальный pinned Debian amd64 release** rclone v1.76.0 (06.11.2026) напрямую из `downloads.rclone.org` с фиксированным SHA-256, не ограничиваясь устаревающим Debian APT. Задача не создаёт удалённых подключений, не удаляет существующий root `rclone.conf`, не создаёт mounts и не выполняет копирование/восстановление данных.

Встроенный начиная с v1.74 новый `rclone gui` запускается как `dh-rclone-gui.service`, systemd с `User=<owner_slug>` (не root). Постоянный конфиг GUI — `/var/lib/digitalhouses/rclone/rclone.conf`, отдельный от прежнего root rclone; сервер работает с правами владельца Samba (группы media/doc) и не имеет доступа к admin-only backup ZFS. Для работы браузера нужны **два LAN-порта** на IP VM: GUI `5580`, RC API `5572`. Они не публикуются через Cloudflare; создание внешнего административного маршрута требует отдельной задачи Access.

Локальная ссылка на портале: `http://<media-ip>:5580/login?url=http%3A%2F%2F<media-ip>%3A5572%2F`. Пользователь: `mediaadmin`, пароль генерируется один раз (48 hex символов), хранится только внутри VM в `/etc/digitalhouses/rclone-gui.env` (root:root, 0600). Посмотреть из PVE root: `qm guest exec 2232 -- cat /etc/digitalhouses/rclone-gui.env` — **не публиковать вывод**. Пароль не передаётся в аргументах процесса, не логируется (rclone `--log-level ERROR`), не совпадает с коротким паролем медиаприложений. При повторном №30 пароль сохраняется. Встроенная проверка подтверждает GUI HTTP 200, отказ API без логина HTTP 401 и успешный авторизованный `core/version`. Интерфейс rclone API эквивалентен возможностям UNIX-пользователя службы; доступ к обоим портам разрешать только в доверенной локальной сети.

Фактическое развёртывание на VM 2232 должно подтверждаться отдельным запуском №30 в режиме `apply + keep + import` и итоговым `PLAY RECAP`; наличие кода само по себе не означает, что служба уже работает.

## Портал DigitalHouses и многопользовательский доступ (08.11.2026)

- Тёмный портал-витрина: каждая карточка приложения открывает отдельную вкладку (`target="_blank"`, `rel="noopener noreferrer"`). Файлы представлены Filestash/Sambee, без дополнительных верхних карточек.
- SMB-адреса `Media` и `Documents` показаны отдельно для Windows (`\\\\IP\\Share`) и macOS (`smb://IP/Share`). У каждого адреса своя иконка копирования; браузеры на HTTP пользуются безопасным fallback копирования.
- На портале показываем только локальную ссылку на Webmin `https://<media-ip>:10000/` (в новой вкладке). Внешний административный адрес `https://<site-id>-pve-mediaserver-admin.digitalhouses.vip/` продолжает работать через Cloudflare Access, но **не выводится на страницу медиасервера**. Webmin принимает оба Host/Referer и не перенаправляет локальных пользователей на внешний домен.
- Штаты Samba `[Media]` и `[Documents]` теперь принимают членство `@media_group` / `@doc_group`; `DigitalHouses` и `Backups` остаются только для `owner_admin`. Ansible-3 управляет только базовыми владельцем и администратором, не удаляет Webmin-пользователей на повторном запуске.
- Webmin — официальный upstream APT с закреплённым ключом; модульная панель `useradmin` + `samba`, Webmin-only пароль root хранится в guest-only `/etc/digitalhouses/webmin-admin-password` (0600). Синхронизация Unix/Samba при операциях Webmin включается; пароль исходного владельца и root Unix не меняется. Если администрирование Webmin не опубликовано через Cloudflare, внешний доступ отсутствует.
- **Граница ответственности:** никаких изменений исходного кода сторонних агентов и приложений. Публикацию через Cloudflare выполнять только после проверки Access-ограничений и HTTPS origin.

## Режим и два действия в Semaphore (safe defaults)

- VM: keep — существующая проверенная VM; create — только отсутствующая; recreate — удалить только собственную VM и её виртуальные диски, затем единый create.
- Disk: import — импорт существующего ZFS без стирания; erase — стереть только диск за выделенным SATA-контроллером и создать ZFS.

**Параметры CPU в №30 (Survey, PR #42):** два необязательных независимых целочисленных поля `DH_MEDIA_VM_CPU_PERCENT` (общая квота всей PVE VM) и `DH_MEDIA_TRANSCODE_CPU_PERCENT` (общая квота Plex + Jellyfin). Значение `150` означает 1,5 логического ядра; допустимы 25–(cores × 100) процентов. Пустое поле берёт число из приватного site manifest: сейчас `cpu_limit: 1.5` → 150% VM и `transcode_cpu_limit: 1.0` → 100% медиаплееров. Никакого неявного изменения этих настроек при обычном audit: №30 только выводит выбранное значение. В **неопубликованном** `media-server-deploy.yml` PVE лимит передаётся в `qm set --cpulimit`, а для Plex/Jellyfin настроен единый `dhtranscode.slice` с `CPUQuota=N%`; после apply предусмотрено чтение PVE конфигурации и cgroup `cpu.max`. Реальные изменения CPU ещё не проверялись на VM.

Шесть комбинаций — не шесть реализаций. Выбор в Semaphore достаточен
как разрешение. Для VM сохраняются ограничения на чужие VM и PCI.
В дисковой ветке Import нет старых preflight; в Erase сохраняется
только защита системного диска и однозначный выбор SATA.
Import никогда не переходит в Erase автоматически.

## Этапы реализации

1. Каноническая site identity, доверенный PVE SSH ключ после №10, точная VM/PCI конфигурация.
2. Штатный Ansible и qm: keep/create/recreate, Debian 13, 2 vCPU, RAM 4096, boot 64 GiB, balloon off, GPU/SATA passthrough из private site manifest.
3. QGA для доверенного SSH ключа guest, только один SATA-диск, native zpool/zfs, declared datasets, директории, автомонтирование. Никаких дополнительных технических approvals.
4. Plex, Jellyfin, qBittorrent, Radarr, Sonarr, Prowlarr, Filestash, Sambee, локальный портал и авторизация native API/CLI. При необходимости собственного Python сначала отдельное техническое согласование; не копировать старые custom Python tools.
5. SMB shares Media, Documents, Backups, DigitalHouses; Bonjour, Plex autoscan, медиапути, CPU/ARC и GPU. Общий пользовательский пароль 6–8 символов, первичный — 8, без логирования; Plex со своей учёткой. Нельзя открывать смену пароля через незащищённый HTTP.
6. №81 как приёмка внутри №30: VM, QGA, ZFS, GPU, SMB, приложения/логины/порты, библиотека, повторное исполнение.

## Подготовка явного destructive E2E `recreate + erase` (2026-11-06)

Владелец запросил разрушительный запуск №30 для существующей **только** VM `2232` и диска за SATA PCI `0000:2b:00.0`. Аудит #85 подтвердил пул `serzhan-pool`, GUID `40733622006301358`, ONLINE и непустые `media/downloads` и отдельный `downloads` dataset; `erase` уничтожит также документы, резервные копии и все остальные datasets этого пула. **Фактический `recreate + erase` не выполнялся; обновлённый apply допускается только в Draft-коде и ещё не зарегистрирован в Semaphore.**

Подготовлены две независимые проверки перед разрушением: (1) ещё на **старой работающей VM, до `qm shutdown/destroy`**, проверка имени, описания, отсутствия lock, двух PCI devices, QGA, GUID ровно существующего пула, ONLINE, единственного ZFS vdev и отсутствия ошибок; (2) уже внутри новой VM, **до остановки служб, `zpool destroy`, `wipefs`**, повторное сопоставление единственного SATA-диска с исходным именем и GUID по активному пулу либо read-only ZFS label scan. Если диск поменяли между стадиями, выполнение прервётся до стирания. Импорт чужого пула не допускается.

Образ Debian 13 с официальным SHA512 теперь предварительно скачивается на PVE **до удаления старой VM**; в `tasks/media-vm-apply.yml` после `qm destroy` нет повторных сетевых загрузок, а хэш файла проверяется перед `qm importdisk`. Дополнительно `create` отвергается для существующей VM. Private site manifest пополнен обязательной директорией `media/downloads` (PR DigitalHouses/site-serzhan-home#3), иначе первый запуск qBittorrent на пустом ZFS не смог бы стартовать.

**После erase ZFS GUID всегда меняется:** native задача считывает и сообщает новый GUID в журнале. Для следующего `import` потребуется синхронизировать поле `media_vm.storage.import_pool_guid` в приватном site-repo с фактическим новым GUID; нельзя использовать старый GUID молча. Автоматического коммита в private repo во время разрушительного запуска нет.

`tests/media30-recreate-erase-guard.yml` проверяет точное совпадение, чужой и неоднозначный пул (отказы ожидаемы), а также порядок preflight → download → VM lifecycle → disk erase; все проверки выполняются на DEV без изменений гостя. Это не live E2E; после удаления искусственных блокировок реальную корректность установочного пути должна подтвердить встроенная №81.

## Стандарт адреса медиасервера — S24 (11.11.2026)

Нормативны последние октеты, а не вся сеть: HOME Media — **.223/VM2223**;
CORE Media — **.243/VM2243**. Подсеть — своя у каждого объекта.
Например, у владельца `192.168.11.223`, у клиента с сетью
`192.168.22.0/24` — `192.168.22.223`.
Полная таблица S24 в [ANSIBLE_STANDARDS.md](../ANSIBLE_STANDARDS.md).

В HOME Semaphore №30 поле `DH_MEDIA_IP` по умолчанию равно **`223`**.
№30 теперь рассчитывает `.223/VM2223` **даже если старый site manifest
содержит `.250/VM2250`**. Не использовать исторический адрес манифеста
вместо нормативного значения по умолчанию. Указание другого IP вручную
считается явным исключением для legacy/специальной операции;
автоматически менять действующий гостевой IP нельзя.

- `audit`: показать выбранную целевую VM/IP и реальные PCI/VM PVE, без изменений.
- `apply + create`: создать отсутствующую VM c выбранными IP/VMID.
- `apply + keep`: отказать при попытке незаметно изменить IP существующей VM.
- `apply + recreate`: разрушительная операция только по явному выбору.
- Сохраняется правило VMID = 2000 + последний октет IPv4. Внутри
  site-repo новые IP и VMID записываются только после успешной приёмки.

**DHCP-диапазон и резервации контролирует владелец объекта.**
№30 не проверяет DHCP pool и не блокирует создание VM из-за
пересечения статического IP с диапазоном динамической выдачи.
Остаются проверки формата IP, сети объекта и совпадения с PVE/шлюзом.

**Текущий legacy-сервер не изменён:** VM2250 на старом PVE
`192.168.11.230` по-прежнему использует `192.168.11.250`.
Новый HOME медиасервер `.223/VM2223` требует отдельной проверки
физических PCI-ресурсов и свободного адреса. Изменение документации
не означает переноса данных или создания новой VM.

## PBS 4.2+ на медиасервере (08.11.2026)

В №30 после установки rclone добавлен общий native-блок `tasks/media30-pbs-apply.yml`, который также запускается точечно из уже существующего №33 (`playbooks/media-rclone-gui.yml`) на существующей VM. Это **установка сервера**, а не настройка резервных копий.

- На Debian 13 Trixie amd64 — **только** `proxmox-backup-server` из официального `pbs-no-subscription` APT репозитория. Метапакет `proxmox-backup` **не ставится**: ядро гостя, GPU и ZFS из Debian сохраняются. Публичный Proxmox keyring берётся по HTTPS с официальной SHA256 и применяется как отдельный `Signed-By` без `apt-key`.
- Пакет ставится через native Ansible `apt` (с минимальной версией >=4.2); `dpkg-query` и Ansible `version` требуют **не ниже 4.2**. Проверяются `proxmox-backup.service` и `proxmox-backup-proxy.service`, локальная HTTPS-страница `127.0.0.1:8007`.
- На портале медиасервера появляется ссылка **`https://<media-ip>:8007/`** (LAN, self-signed TLS); штатная учётная запись `root@pam` использует пароль Linux root VM. Credential `DH_PBS_ADMIN_PASSWORD` из №05 пока **не расходуется**, `admin@pbs` отдельно не создаётся; настройка пользователей и API токенов — будущая согласованная задача.
- Не создаются datastore и ZFS dataset/quota, не меняются диски, не настраиваются локальные/облачные PVE backup jobs, нет PBS GC/prune/verify jobs или публикации через Cloudflare. Для однотипной схемы хранения и 70/30 квот потребуется отдельный этап, с сохранением медиа данных.
- На mini-PC со 16 ГБ RAM и медиасервисами PBS будет делить ресурсы. Минимум, рекомендуемый Proxmox для PBS без учёта медиа — 4 GiB RAM и 4 ядра; нагрузку/квоты нужно оценить до использования хранилища в качестве производственного PBS.

Тест: `ansible-playbook tests/media30-pbs.yml`; guest: `qm guest exec <vmid> -- proxmox-backup-manager versions`. Отдельный playbook для этого сервиса не создаётся — используется текущий точечный шаблон №33, а штатное развёртывание №30 включает PBS автоматически.


## Привязка VMID медиасервера к IP (2026-11-09)

Согласно стандарту один media VMID вычисляется как `2000 + последний октет IPv4`. Например, `192.168.11.232 → 2232`, `192.168.11.250 → 2250`, `192.168.22.250 → 2250`. Поле `DH_MEDIA_IP` остаётся прежним; нового Survey поля VMID не требуется.

Реализация №30 подставляет VMID и IP в единый in-memory `media_spec`; после успешного apply/accept меняет в приватном `media_vm.yml` **оба поля атомарно одним GitHub commit (optimistic SHA)**, не трогая другие настройки. В режиме audit никаких изменений. Проверки VMID существующих гостей, PCI ownership и отказа `keep` при несовпадающем IP сохраняются. Назначение нового IP **не перенумеровывает** старую VM и не позволяет двум VM на одном PVE одновременно пробросить один SATA/GPU контроллер. Для двух медиасерверов всё ещё нужны независимые физические ресурсы и декларации.
